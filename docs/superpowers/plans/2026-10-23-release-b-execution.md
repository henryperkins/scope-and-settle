## T06: make this the next executable brief

### Data and interfaces

Keep `getScopeContext(ctx): ScopeContext` and `acknowledgeScope(ctx, snapshotId): ScopeAcknowledgement`. Add explicit internal service operations for publishing a baseline/rate snapshot and issuing its client acknowledgement access. HTTP bodies may identify a resource and expected revision, never an actor, project, run, or trusted provenance.

Use additive recorded migrations after the current last migration (currently 3; recheck before implementation):

- `scope_snapshots`: ID, project/run, monotonic integer version, legacy revision label, immutable clauses JSON, content hash, source/provenance kind, optional source reference, creator and captured time. Clause identity is `(snapshotId, clauseId)`; retaining a clause ID in a later snapshot does not rewrite an earlier clause. Enforce unique `(project_id, run_id, version)` and use a distinct capture identity for historical snapshots where their old relative order is unknown.
- `rate_card_snapshots`: ID, project/run, monotonic integer version, currency, immutable entries JSON, content hash, provenance and capture time. A rate reference is `(rateSnapshotId, rateCardId)`, not a globally current ID. Enforce unique `(project_id, run_id, version)`.
- `run_scope_heads`: project/run, current scope and rate snapshot IDs, monotonically increasing context version. Resolve this head only after authenticating the active run. Frozen judging runs derive their first head from `judge_runs.project_json`; they never inherit later global edits.
- `scope_acknowledgements`: ID, project/run, exact snapshot ID, server-derived client actor/grant, explicit consent and timestamp. Append only. Idempotent repeat by the same authority returns its existing record. Acknowledgement never writes `approvals`, invoice operations, or a proposal status.
- Assessment and proposal context: retain `scopeSnapshotId`, `rateSnapshotId`, `commitmentFingerprint` and immutable commitment references. New approvals point to that exact proposal context. Use nullable/additive columns or companion records for old rows; never rewrite an existing `proposal_revisions.snapshot_json` or invent missing provenance.

`ScopeContext` should expose `{ scopeSnapshot, rateSnapshot, acknowledgement, commitments, contextFingerprint }`. Include `provenance.kind`, source time if known, capture time, and `acknowledgement.state: supplied_unacknowledged | acknowledged`. Commitments identify source type, resource ID/revision, immutable terms, approval evidence, work disposition and separate current financial/delivery observations. T20 can add retainer-work records through this union later without pretending they are invoices.

### Migration and version inheritance

Import current ordinary-run and frozen judging-run snapshots from their actual stored JSON. Historical assessment input and proposal JSON can each supply their own snapshot evidence; use scoped content hashes to distinguish conflicting bodies sharing a legacy revision label. Record `legacy_import` and capture time, not a fabricated historical creation or client acknowledgement. Missing historical context remains explicitly unknown. No historical row is assigned today's baseline merely to fill a non-null field.

Preserve the current supplied synthetic brief contract: unacknowledged does not mean app-acknowledged, and introducing acknowledgement must not retroactively prohibit the already approved 0.3 workflow. Show provenance clearly. An acknowledgement of snapshot A does not acknowledge replacement B, does not approve a change order, and does not authorize rates or automation.

Extend pending-proposal staleness to the scope/rate context pair. Changing either requires designer review and a new proposal revision before approval; an old link cannot become valid again. Approved and invoiced revisions continue using their captured terms. New assessments use the current run head plus approved commitments; assessment-to-draft/submit checks reject stale input or require explicit re-review when that context changed. Rate amounts always resolve from the assessment/proposal's selected rate snapshot.

Do not insert new fields into the legacy `ProjectView` hash path without a compatibility projection. Keep the existing field order/projection for v1 policies (name, file, currency, scope label/clauses, rate card as currently serialized), or version the hash and migrate it without adding authorization. New policy snapshots explicitly bind scope/rate IDs. A new approved addition changes assessment commitments/cache state but must not by itself invalidate the owner's unchanged catalogue/limit policy. Preserve `quoted_minor` cumulative spend across all versions.

### Exact client grants and surfaces

Add `ResourceGrant.kind = 'scope'` bound to one snapshot and its revision; keep `project` and `change_order` distinct. Extend `context.ts`, `sessions.ts`, invitations, `judgeAccess.ts`, `judging.ts` and renewal validation so scope clients are accepted only for scope read/acknowledge. Existing client validation currently assumes a proposal in all these layers. Preserve legacy column interpretation for old sessions/grants; explicit `grant_kind/resource_id/resource_revision` additions are safer than overloading `change_order_id` with snapshot IDs. Deny cross-kind resource use and recheck parent revocation/reset/expiry after awaits.

The private portal has separate hashed authority. Display the supplied/acknowledged scope there, but do not treat a broad portal session as an exact acknowledgement grant. Issue a narrow scope capability to the eligible portal through a server-side relationship, with its own expiry and exact snapshot binding; no client-supplied actor upgrade. Do not require portal users to have Figma accounts.

Designer UI: show selected scope/rate versions, provenance, acknowledgement state, and separate approved additions; offer issuing acknowledgement access. Client scope view: show the exact immutable snapshot and explicit acknowledgement control, distinct from proposal approval. Proposal review and portal cards display the versions actually used. Preserve old review URLs and renewal behavior. The root template edit remains restricted by `canEditScope`; do not unlock frozen judging-run edits incidentally.

## T07: request items and closed-loop reservations

The public Figma entry `assessRequest(ctx, {commentId, evidenceSnapshotId?})` should fetch authoritative comments then call a common request service. Add a trusted portal/worker entry over the existing request ID; portal requests have no Figma comment ID and must not be forced into a fake comment. Persist source identity `(project, run, source, fileKey when applicable, rootId)` and content/reply versions. Group direct replies using authoritative `parentId`; retain provider source IDs, not only generated message IDs.

Persist server-generated `request_items`, versioned assessment-item results, `proposal_item_reservations`, `request_order_links`, and `duplicate_decisions`. The model suggests decomposition/evidence; it never assigns authoritative item/reservation IDs. Exact unchanged source/item matches reuse IDs. If a new decomposition splits/merges or paraphrases an already reserved item, preserve its lineage and block pricing until a designer resolves it. A fresh model answer cannot delete or replace a reservation.

Refine `reserveProposalItems(ctx, itemIds, operationId)` to return a persisted operation/order binding: `{ operationId, orderId, itemIds, assessmentId, expectedContextFingerprint }`. Bind the idempotency key to actor/project/run plus a hash of the selected IDs and terms; a conflicting reuse fails. Draft creation and active reservations must commit together (use one outer transaction; the current transaction helper does not supply nested transactions). A unique active reservation per scoped item is the database invariant. Route manual draft, auto-quote and MCP draft through this same operation.

Lifecycle: draft/submitted items remain reserved; exact client approval converts them into committed items. Failed creation rolls back the reservation; an explicit draft abandonment/supersession releases or transfers only its own unapproved reservation and records why. Editing a draft cannot silently drop/reassign its items. Invoice cancellation, refund, payment reversal or an uncertain provider result does **not** cancel the work commitment or release it. Reopening cancelled work requires an explicit recorded work-disposition decision and a linked new proposal; until that distinction exists, keep the item blocked for review.

Semantic duplicates are candidate links to immutable approved commitments, never an asserted deterministic match. Show the evidence and original record. Record designer resolution (`same_commitment`, `distinct_work`, or unresolved) with actor, reason and both item/context revisions. Unresolved suspicion cannot enter automatic or MCP pricing. Exact duplicates remain blocked regardless of model output; fuzzy matching cannot guarantee all paraphrases are detected and must be evaluated honestly.

Per-item classifications preserve the current three categories with an optional existing-commitment reference. Evidence is a discriminated reference to a scope clause or approved change revision; validate exact quotes against that server-owned snapshot. Included, ambiguous and same-commitment items have zero billable lines. Resolve allowed rate IDs and integer quantities on the server. A manual override remains visibly designer-priced and cannot become automatic policy consent.

Extend the portal beyond `agent_requests.order_id/quote_revision`: multiple partial proposals require an explicit scoped join and list of published revision references. Backfill old single links without changing them. Keep cumulative allowance accounting monotonic; replacing/revising a quote cannot erase earlier published amounts. Do not enable multi-proposal creation while portal approval can resolve only one order pointer.

## T08: immutable design evidence and cache semantics

`DesignEvidenceInput` carries the configured file key, node IDs, capture time, bounded text/component/layout metadata and optional PNG; server records receive time separately. Authenticate membership first, fetch allowed authoritative nodes, and revalidate actor/run after awaits. Wrong file, unavailable node, invalid/future capture time, oversized bytes or anchor mismatch cannot silently produce trusted evidence. An anchor mismatch requires explicit selection of relevance, retained as a reviewer assertion.

Store snapshot hash, file/node references, available provider version metadata, collection source, verification status and freshness. A PNG remains client-supplied pixels even when the node exists; never call it an independently verified rendering. No image must be sent for automatic text-only assessment unless that immutable evidence was explicitly selected. Failed REST node access yields an explicit unavailable/limited state, not fabricated verification. Optional bytes use scoped storage and the run reset lifecycle.

One cache key must hash normalized authoritative request/replies and versions, selected item lineage, scope snapshot, rate snapshot, approved commitment/disposition fingerprint, evidence hash/version/selected relevance, provider/model/reasoning settings, prompt/schema version and manual-versus-automatic mode. Validate current authority, freshness and policy independently on a cache hit. Approval, work disposition, request reply, relevant evidence or prompt changes invalidate eligibility. Financial observations alone need not invalidate semantic scope results unless they changed an explicit work disposition. Coalesce concurrent identical inference through the same paid-work reservation; cache reuse must not bypass item reservations or current publication checks.

## T10–T12: reviewed actions, connector security and status cards

`reviewed_actions` must persist initiator, required human confirmer, project/run, action/resource/revision, exact text/terms hash, expiry, state, operation key, confirmation audit and provider/reconciliation result. Preparation has no outbound side effect. Confirmation requires a separately authenticated eligible application actor and atomically transitions `prepared -> executing`; concurrent/replayed confirms return the stored operation result/state. Do not accept actor fields or `confirmed: true` from tool JSON.

Use the existing `agent_outbox`/provider adapters for send and recovery, with explicit authority type (`policy` or `human_review`). Reviewed reminders share cooldown/deduplication with automatic reminders. Read authoritative invoice state and verify immutable merchant/currency/amount/revision immediately before an eligible action, then recheck local authority. Unknown send outcomes stay uncertain; no blind retry. A PayPal cancel is an invoice action, not a scope/work cancellation. Actual reminder limits and supported payload behavior must be checked against official PayPal documentation during T10 before implementation/live qualification.

T11 local implementation can proceed behind disabled deployment flags while actual Figma connector availability remains unverified. Before dependency selection, check official MCP SDK Node 24/Streamable HTTP documentation and official Figma custom-connector transport/auth requirements; pin the selected package and record the source/date. This preflight did not perform that compatibility check or make account/provider calls.

Connector records store only a random credential digest, project/run, allowed tools, parent authority, expiry/revocation and budget restrictions. Extend the private authority registry to revalidate that connector after await boundaries; never promote it to unrestricted designer/session authority. Read tools cannot issue invitations, leak portal links/provider credentials/raw images, or trigger paid work. Draft tools enforce T07 reservations and cannot grant client approval. Reject injected actor/project/run fields, unsupported schema versions and stale revisions. Use a restricted MCP transport route with Origin validation, bounded requests, explicit methods and authentication; do not inherit the application's current wildcard CORS helper by default. Treat all comments and tool content as data.

T12 adds preparation-only MCP tools. Bind a connector-prepared action to the eligible application confirmer, not a fictional equality between connector ID and human actor. Review URLs contain opaque identifiers, not bearer credentials; GET only displays the preview. App confirmation must use application authentication and same-origin/CSRF protection as appropriate, exact displayed terms and single-use state. Generic MCP tool consent cannot confirm the action. `issue_approved_invoice` additionally requires the persisted exact client approval and delegates to existing `ensureInvoice` recovery. Preserve the existing portal/review client's direct explicit approval-and-invoice flow.

Status-card identity must include project/run/order, not a title match. Store the node mapping/plugin data and update idempotently; if the mapped node was deleted create a replacement and update the mapping. Display approval, payment and delivery separately with last-observed time/cached label. Monetary display defaults off. Link to an authenticated app landing page without invitation/renewal/portal secrets. Native execution is explicit or while the plugin runs; a closed plugin cannot claim to keep the canvas current. Dev Resource writes remain disabled until independently verified.
