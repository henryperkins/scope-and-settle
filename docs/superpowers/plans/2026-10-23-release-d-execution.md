# Release D architecture and access preflight

Research date: 2026-10-23. Scope: T18–T22 after Releases B/C. This is a design and public-documentation review, not implementation or account qualification. No authenticated provider calls, secrets, real databases, builds, or tests were used. Recommendations below are proposed application architecture; cited provider requirements are distinguished from recommendations. No new account or paid service is selected.

## Decision

Keep Node 24, TypeScript, vanilla browser UI, `node:sqlite`, and one process per database. Implement a standards-based OIDC adapter using maintained `openid-client` v6, with the user's existing/chosen issuer supplied as deployment configuration. Use the issuer directly for MCP authorization if it meets the required protocol. Otherwise use maintained `oidc-provider` v9 as an application authorization bridge backed by the same verified upstream identity. Do not write a token-issuing OAuth protocol implementation or introduce a frontend framework.

Proceed with schemas, scoped services, fixture adapters, unavailable states, and migration tests while identity configuration and PayPal access are unresolved. Real-customer enablement is a separate gate. Delegated PayPal invoicing and subscriptions require product-specific partner access; current single-merchant sandbox credentials do not establish that access.

## Current source and constraints

Reviewed task-18 through task-22 briefs and `docs/superpowers/plans/2026-10-23-agent-integrations-checklist.md`, plus `context.ts`, `sessions.ts`, `migrations.ts`, `db.ts`, `jobs.ts`, `paypal.ts`, `figma.ts`, `server.ts`, `capabilities.ts`, `env.ts`, and `app/package.json`.

- `context.ts` already creates immutable, server-provenance-bound contexts and rechecks sessions. It derives actor IDs from demo grants/session hashes, not verified identities. Client authorization remains bound to an exact proposal revision.
- `sessions.ts` issues role-bearing invitation/session credentials. Those links explicitly do not identify a person. A real sign-in must not silently promote them into tenant membership.
- `db.ts` resolves the hard-coded `demo` project and per-run snapshots. Tables have no tenant ownership. `getProjectForRun` can fall back to the demo project; that fallback must not exist for real tenants.
- `jobs.ts` routes reconciliation using a global configured merchant/app fingerprint. Its invoice lookup spans orders and operations by invoice ID. That is sufficient only for the bounded current demo; a provider event must not perform a cross-tenant invoice lookup in D.
- `paypal.ts` has a single process token cache and global client credentials; `figma.ts` uses the configured PAT/file. Both need connection-aware adapters. `env.ts` is sandbox-only and rejects live PayPal; preserve this until a separately reviewed production activation.
- T11/T12 MCP and T14–T17 delivery/export implementations are downstream of the reviewed source. Re-inventory their final schemas/routes before the D migration; this document does not claim they are implemented.
- Preserve synthetic demo isolation, USD integer cents, immutable approved terms, exact-revision client consent, uncertain-create recovery, reset tombstones, the existing Baseten/model settings and total $25 allowance. No multi-currency, alternate processor, platform fees, or new paid identity subscription is implied.

Current documentation records bounded earlier sandbox invoice/payment/webhook and Figma observations. Those supersede older memory about unverified callbacks, but are not current account introspection or evidence for any new D operation. Capability evidence must continue to distinguish documented contract, fixtures, actual sandbox access, deployment state, and production access.

## T18: identity and authorization subsystem

### Library choice and deployment seam

The maintainer documents active v6 support for `openid-client`, ESM, Node 20+ baseline, discovery, authorization-code flow, token refresh/introspection/revocation. This fits the existing Node 24 ESM backend. `oidc-provider` actively supports v9 and supplies the OAuth/OIDC server protocol, resource indicators, revocation/introspection and token formats. Its upstream CI selects supported Node versions from a minimum of 22; Node 24 compatibility is supported by that runtime policy, not a local execution result. Pin a published release and lockfile at implementation, then verify Node 24 locally; current repository HEAD versions are not proof of a published release. [openid-client](https://github.com/panva/openid-client), [oidc-provider](https://github.com/panva/node-oidc-provider), [provider CI](https://raw.githubusercontent.com/panva/node-oidc-provider/main/.github/workflows/test.yml), [CI version selection](https://raw.githubusercontent.com/panva/.github/3faba8af3880247be43547787aedd52780c9f946/.github/workflows/node-versions.yml).

`identity.ts` should expose `beginLogin`, `completeLogin`, `getVerifiedIdentity`, and `revokeIdentitySession`. Use authorization code + PKCE S256, state, nonce, exact registered redirects, trusted configured issuer, validated issuer/audience/signatures and bounded transaction expiry. Store identity by `(issuer, subject)`; never auto-link accounts or assign tenant membership using an email/domain claim. Browser sessions should be opaque random credentials with only their digests stored; use HttpOnly/Secure/SameSite cookies plus CSRF/origin checks on mutations. Rotate after sign-in and privilege changes. No upstream token goes to the browser, canvas, MCP response, or export.

Proposed local entities: `identities`, `tenants`, `tenant_memberships`, `project_memberships`, `identity_sessions`, `membership_invitations`, `resource_grants`, `provider_connections`, `connection_bindings`, `provider_capability_evidence`, and `audit_events`. An organization is a tenant. Tenant owners/admins manage memberships and connections; designers operate assigned projects; clients receive explicit project/resource grants. Map those administrative roles into existing domain roles only after authorization checks. A tenant owner is not automatically a client approver.

Invitations contain a digest, tenant/project/resource/revision, intended recipient constraint, expiry, inviter, and redemption audit. Require sign-in and explicit acceptance. A verified email can be an invitation constraint, but the resulting membership binds the verified issuer/subject. Revocation blocks future requests, grants and delegated writes. Do not grant all project records to a client merely because they can approve one proposal. Preserve distinct `scope`, `change_order`, `delivery`, and `retainer_work` grants.

### Tenant migration and every resource boundary

`TenantActorContext` extends the existing context with `tenantId`, verified `identityId`, membership/version and active authorization provenance. Only trusted server constructors can create it. Revalidate after awaited calls before returning private data or executing side effects. Do not accept trusted tenant, merchant, role or connection fields from request bodies.

Build an explicit migration inventory covering every persisted table and every SQL query in final B/C source. Backfill existing records only into a reserved synthetic tenant. Tenant-owned tables need non-null ownership and composite uniqueness/foreign keys connecting tenant, project, run and parent IDs. Rebuild SQLite tables where necessary; validate every existing association before enforcing constraints. Unknown/ambiguous rows fail migration and remain recoverable; do not invent ownership or historical identity. Preserve reset tombstones and invoice-operation keys.

Scope all projects, scopes/rate cards, proposals/revisions, approvals, invoices/operations/observations, grants/invitations/sessions, requests/messages/portals/outbox/policies, Figma evidence/comments/nodes, assessments/caches/AI calls, milestones/delivery/acceptances, reviewed actions, packets/exports, subscriptions/cycles/allowances, refunds/disputes, jobs/receipts, reports and tenant audit records. Explicitly classify deployment-global configuration/runtime rows and the global development AI budget; global administrative access must never become a user query.

Move ID-only domain lookups behind context-required repository functions. Include tenant/project/run and authorization filters in SQL, including joins, update/delete conditions, unique idempotency keys, pagination, aggregates and cache keys. Scope storage paths and signed download resolution too. Return a non-disclosing not-found response for foreign IDs. Scope immutable snapshot JSON references, not just outer rows. Restore requires offline validation of ownership, secret references and tombstones before opening traffic; never reactivate old sessions, jobs or revoked connections by restoring a backup.

Jobs carry tenant/project/run, connection ID+generation, operation ID, actor/delegation reference and target revision. Workers derive and recheck authority from stored associations; payload JSON is data, never authority. Read jobs with their ownership tuple, recheck connection/membership at execution and before any effect, and persist the result only against the leased operation. Read-only financial reconciliation may use a narrowly defined service authority after a human session expires, while a queued publish/refund requires still-valid delegated authority. Continue short transactions and no transaction across network I/O.

For webhooks, first resolve a configured provider app/environment route, verify the original signature with that app's webhook configuration, then locate a unique connection/merchant/resource binding. Quarantine unknown or ambiguous events without fetching arbitrary resources through another tenant's credentials. Dedupe receipts within app/environment/provider event identity and operations within connection/resource identity. Consent revocation disables writes and invalidates queued work. A shared platform webhook may cover multiple merchants; model that explicitly.

### Encrypted connections

`resolveConnection(ctx, provider)` returns an authorized reference including connection ID, provider account ID, environment, granted scopes, generation and capability state. Only the adapter/secret boundary can resolve credential material. Use authenticated encryption (for example AES-256-GCM), unique nonces and AAD containing tenant/connection/provider/environment/version; store key ID, nonce/tag and ciphertext. Keys live outside SQLite/backups/source, supplied by the existing deployment's approved secret facility. Define rotation and recovery before production; no new key-management subscription is selected here.

Key token caches by connection+environment+scope+credential generation; coalesce refresh per connection and atomically rotate refresh tokens. Reconnect must verify the same intended provider identity or require explicit rebind, invalidate old generation/caches and review queued operations. Disconnect revokes provider access where supported, erases usable credentials, blocks future provider actions and retains policy-required financial/audit records. Distinguish local disconnect from confirmed remote revocation.

Figma OAuth is per user; bind the returned `user_id_string` and exact allowed project/file set. Start with required read scopes, request write/webhook scopes only when enabling those features, and reauthorize if permissions expand. Do not assume automatic cumulative scope grants. Treat refresh expiry/revocation and file access loss as reconnect-required. Preserve the demo PAT solely in its isolated synthetic path. Figma requires an OAuth app; callback configuration, app availability and real user/file scope checks remain deployment proof. [OAuth apps](https://developers.figma.com/docs/rest-api/oauth-apps/), [scopes](https://developers.figma.com/docs/rest-api/scopes/).

### MCP OAuth

Treat `/mcp` as a protected resource. Publish protected-resource metadata with canonical resource URI and authorization server metadata, and return correct Bearer challenges. Require OAuth code+PKCE, audience/resource binding, narrow scopes, expiry and current revocation/membership checks. Provider access tokens and browser sessions are not MCP bearer tokens. Preserve T12 human-confirmation action preparation: OAuth tool scope cannot approve a proposal or execute a refund.

The current MCP 2026-07-28 spec prefers Client ID Metadata Documents; pre-registration is also supported and dynamic registration is deprecated compatibility. Verify the actual Figma client and pinned server library combination before choosing registration mode. `oidc-provider` lists CIMD as experimental: either use tested pre-registration where supported, or explicitly pin/acknowledge the draft and test metadata fetching restrictions. Do not claim all MCP clients work from a fixture test. The bridge still needs durable adapter storage, production login/consent interactions, signing-key rotation and account lookup; library inclusion alone is not a complete identity service. [MCP authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization), [provider integration documentation](https://raw.githubusercontent.com/panva/node-oidc-provider/main/docs/README.md).

## PayPal merchant consent and product gates

Recommended connection is partner referral onboarding **before payment**, subject to actual approved partner access. Record app/environment, partner identity, seller merchant ID, primary email, permissions, product/capability state, consent time and sanitized proof. Validate server-side merchant status; a redirect or asserted query parameter cannot activate a connection. Watch verified onboarding-completed and partner-consent-revoked events. PayPal's software-embedded onboarding option lists disputes and reports as unsupported, so it is not a suitable shortcut for this roadmap. [Onboarding options](https://developer.paypal.com/platforms/seller-onboarding/), [before-payment requirements](https://developer.paypal.com/platforms/seller-onboarding/before-payment/).

| --- | --- | --- |

[Guide](https://developer.paypal.com/platforms/invoicing/integrate) | Approved partner product and actual seller grant; create/send/get/reconcile under the correct seller in sandbox; separate live approval |
| Delegated subscriptions | Select partners, onboarding and BN code; Catalog Products and Subscriptions APIs; `PayPal-Auth-Assertion`. | Actual refund | Payments v2 endpoint refunds a captured payment. Extend the registry to tenant connection + environment + exact operation + evidence record + explicit deployment flag. Add currently absent operations such as subscription transaction listing and merchant-status retrieval only with reviewed contracts. PayPal consent identifies merchant authority; application identity and exact proposal/work authorization remain separate.

## T19/T20: cycles, allowance and work

Persist immutable `retainer_plan_versions` (product/plan, USD price, cadence, whole units and terms), `subscriptions`, `subscription_observations`, `billing_cycles`, `cycle_payment_allocations`, `allowance_entries`, `allowance_reservations` and versioned `retainer_work`. Every record carries tenant/project/merchant connection ownership. Keep the recurring service agreement separate from billing for use of this application.

The reconciliation adapter retrieves subscription state and its transaction list, validating merchant association, plan version, USD amounts and completed payment evidence. Store transaction identifiers, provider times, retrieval time and allocation to the exact local cycle. Do not credit on `ACTIVE`, approval redirect, a webhook alone, or `last_payment` alone. If retries, setup fees, arrears or plan changes make allocation ambiguous, require review. Initial supported terms should use fixed cadence, no trial/setup charge/proration and explicit whole units. [Subscriptions API](https://developer.paypal.com/api/subscriptions/v1/), [transaction listing](https://developer.paypal.com/api/subscriptions/v1/subscriptions-transactions).

Grant once under a unique `(tenant, subscription, plan version, cycle)` key only after the paid-cycle basis is verified. Deduplicate each provider transaction allocation. Retain both effective provider time and observation time. Reversals/refunds append adjustments and flag affected commitments for review; do not delete consumed work/history. Pending/failed cycles grant nothing; cancellation/suspension blocks new grants according to terms, without erasing previously authorized work.

On exact-revision `retainer_work` client authorization, use one `BEGIN IMMEDIATE` transaction to check cycle eligibility and reserve units. Check available = grants + approved adjustments − consumed − active reservations. Consume once on the defined delivery acceptance; release unused reservations on cancellation. Unique work/reservation/acceptance keys plus conditional writes prevent two requests spending the last unit. A reservation remains attached to its original paid cycle while work crosses a boundary; unused unreserved units expire with no rollover. Releasing an old-cycle reservation does not create current-cycle units. Cancellation, refund and reversal policies for already reserved work must be in the agreed terms.

Retainer delivery verifies the authorized reservation and paid basis instead of creating a zero-dollar invoice. Insufficient units produce a separate change-order proposal with fresh client approval and ordinary invoice recovery. Subscription approval/saved payment method is never overage authorization. The client UI shows available/reserved/consumed/expired/review-required units, cycle dates and linked work.

## T21: refunds, disputes and supported fallback

Use a typed payment reference (`invoice_payment`, `capture`, or another specifically supported resource), resource ID, merchant/environment and authoritative association proof. `prepareRefund` validates amount and creates a T10 preview bound to payment state/remaining refundable amount, connection generation and explicit human authorization. Execution rechecks, records the attempt and uses route-supported idempotency. Unknown outcomes reconcile before retry; do not assume a header is supported on every endpoint. Read back status and refund identity before marking verified. Prevent concurrent partial refunds exceeding the available amount. Never probe an invoice transaction ID through an unrelated refund API as if the resource type were established.

If this invoicing flow has no verified refundable API resource, expose **Refund in PayPal** instructions with an application pending reconciliation record, not an enabled API refund button. The merchant opens PayPal Activity, locates the original payment, chooses Issue a refund, reviews the amount and submits. PayPal documents full/partial refunds within 180 days; the live account UI determines current eligibility. Do not substitute Send Money. [Merchant procedure](https://www.paypal.com/us/cshelp/article/how-do-i-issue-a-refund-help101).

After the merchant reports completion, retrieve the authoritative invoice and available linked payment/refund details through authorized APIs. Match seller, original payment, currency, amounts and refund ID; distinguish PayPal financial refunds from external bookkeeping records. A user-entered reference, screenshot or invoice `REFUNDED` label alone is insufficient financial proof. If API read-back cannot establish movement, record `merchant_reported / verification_pending`, preserve receipt evidence privately and require verified provider reconciliation/support evidence before presenting it as confirmed. Never auto-call invoice `/refunds` to manufacture the proof. Record external refunds only as a separately approved bookkeeping action supported by actual external-refund evidence.

Dispute preparation binds an immutable T17 packet version/hash and current merchant/dispute/transaction identity. Fetch fresh details and allow only the action advertised by current provider links/state; recheck immediately before submission. Evidence submission, sending a message, settlement offer, claim acceptance and escalation are separate human authorizations. Never expose sandbox adjudication helpers in live mode. Maintain `prepared`, `submitted`, `verified`, `failed`, `unknown`, and `unavailable` states; evidence submission is not an outcome guarantee. [Current dispute action eligibility](https://developer.paypal.com/platforms/disputes/handle-disputes/use-disputes-api/).

## T22: reporting and operations

`getStudioReport(ctx, {from,to})` derives tenant-scoped metrics from canonical local obligations, invoice identities, verified payment/refund observations, subscriptions/cycle allocations and allowance/delivery events. Report approval obligations separately from billed amounts: sum installment invoices once, never add the proposal total again. Count shared transactions/refunds once by merchant/environment/provider identity. Separate invoice cash, subscription cash and allowance units; do not count an allowance grant as revenue. Keep pending/unknown/review-required financial observations visible.

Use explicit half-open UTC periods, provider effective dates where present, observation timestamps and freshness labels. Missing dates remain unknown and excluded from duration denominators with counts. Show operational approval-to-payment timing rather than claiming recognized accounting revenue or measured time savings. Fees require verified reporting data and remain unavailable otherwise; delayed reports never authorize immediate delivery/payment state.

Define a user-approved retention policy by data class before real customer use: optional design evidence/snapshots, operational content, audit/financial records and backups. Configure durations rather than inventing legal periods. Implement authenticated export/deletion requests, selective purge, financial/audit hold handling, revoked-connection behavior and a backup restore rehearsal. Backup restores retain tenant boundaries and apply revocation/deletion tombstones before service resumes. Prove outside-designer workflow usability and collect willingness-to-pay feedback separately from revenue claims.

## Implementation sequence and acceptance evidence

1. After C source stabilizes, inventory every table/query/route/cache/export/job and write `docs/STUDIO-ACCESS-DESIGN.md`; freeze migration fixtures and define issuer/connection interfaces.
2. Add identity/tenant schema and context constructors; migrate synthetic records into demo tenant; refactor every resource service and SQL query. No partial real-tenant rollout.
3. Add encrypted connections, refresh/disconnect lifecycle, tenant-aware adapters and webhook/job routing. Add the OIDC login flow and MCP authorization integration.
4. Add PayPal onboarding state machine and capability evidence, with real operations unavailable until access proof. Complete two-identity isolation, reconnect/revocation and encrypted backup/restore proof before customer data.
5. Implement T19 subscription reconciliation/paid cycles, then T20 transactional reservations and retainer delivery. Keep fixture and real renewal results separate.
6. Implement T21 previews/state machines, eligible API routes and merchant-led fallback; add provider operations only after their individual access records.
7. Implement T22 operational reporting and retention controls, cross-tenant browser checks, independent readiness review and full regression. Production activation remains separately reviewed.
