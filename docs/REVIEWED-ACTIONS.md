# Reviewed outbound actions

The designer request inbox offers **Review outbound action**. Preparation reads current authoritative state and saves a ten-minute immutable preview; it does not send a comment or notification, create an executable outbox entry, reserve an invoice send, or run an AI assessment. Changed request/source references require a refresh. The preview shows the exact Figma text (including the visible tracking marker), or the exact approved invoice revision, financial terms and recipients.

Confirm in the authenticated designer application with the required consent checkbox. The server binds confirmation to the eligible actor and parent session/grant, project/run, exact displayed preview hash, expiry, source and resource revision. Opening a review link only reads the saved record. Connector JSON and `confirmed:true` do not establish human authority. The async service is `prepareReviewedAction(ctx, input): Promise<ActionPreview>`; `confirmReviewedAction(ctx, id, previewHash)` is behind the application confirmation route. The route requires the configured application Origin and `{previewHash, consent:true}`. Set `PUBLIC_BASE_URL` to the deployed application's actual origin.

Enable reviewed Figma posting explicitly with `FIGMA_COMMENT_POSTING_ENABLED=true` and a token granted `file_comments:write`; read-only deployments only need `file_comments:read`. This build uses the configured backend personal token rather than requesting OAuth scopes interactively. Existing automatic policies retain their separate explicit notification permissions. Clarifications reply only to a verified actual root in the configured file. Successful acknowledgements retain the real provider reply and posting identity. **Refresh reply thread for reassessment** brings that root and subsequent client replies back into the inbox. Refresh is read-only; reassessment remains an explicit paid-work decision. Known outgoing reply IDs/markers are excluded from client intake.

PayPal supplies reminder/cancellation subject and note; custom wording is ignored. Notification recipient choices are explicit. Only existing invoice CCs are accepted, and the current adapter supports the complete existing CC set (or none when none exist). Partial/empty suppression of existing CCs is deliberately unavailable pending provider qualification. Automatic policy reminders notify only the configured buyer and reject invoices with existing CCs that require additional consent.

Manual and policy invoice actions share one durable invoice reservation, uncertain-send hold, provider backoff and conservative reminder cadence: at least 24 hours after approval and between attempted reminders. Automatic reminders also retain their lifetime cap of two per invoice. PayPal documents a two-reminder daily limit; provider day/reset semantics and out-of-application sends are not inferred. Honor 429/Retry-After and review any provider rejection. Invoice dispatch requires a fresh authoritative SENT/UNPAID invoice with matching immutable merchant, currency, full amount and item terms and no payment/refund activity. Paid, partial, pending, cancelled, draft, scheduled and unknown states are rejected.

Cancellation requires its own preview and explicit confirmation. The invoice reservation remains active throughout provider read-back. Matching authoritative CANCELLED can reconcile a lost acknowledgement; this proves the financial state, not this attempt's cause or notification delivery. Every matching CANCELLED read-back, whether in the original confirmation, a later confirmation of an uncertain cancellation or one that restart recovery left uncertain, then updates local payment status through the serialized payment refresh: one fresh read, never a send. That update needs current application authority and the exact stored order, approved revision, invoice and immutable terms, but not the ten-minute preview expiry or a current request/source, which fence only new sends. If it cannot be applied, the action stays reconciled with the invoice reservation released and its result reports the local update as pending; confirming again or **Check payment** retries only the read. Cancellation never revokes approved work, releases committed item reservations, refunds money or records payment.

Execution is single use. A repeated confirmation returns its saved result or reconciliation state. Claims, dispatch boundaries, provider acknowledgements and results are durable; interrupted execution becomes uncertain and cannot be resent automatically. Notification uncertainty survives policy changes, warning acknowledgement, dismissal and revocation. Reminder uncertainty cannot be resolved merely because the invoice remains unpaid. Figma marker text alone is not a receipt: without a trusted posting-identity receipt, a lost acknowledgement remains uncertain for provider inspection. An acknowledged API request does not establish recipient delivery.

Local tests and browsers use isolated synthetic providers. Actual Figma write grants, real sandbox notifications/cancellation, recipient delivery, hosted operation and physical native-plugin behavior require separate recipient-aware qualification. The application is currently one process per database. Historical unavailable-source/old-item invalidation is tracked separately in T11.

Provider contracts: [Figma comments](https://developers.figma.com/docs/rest-api/comments-endpoints/), [PayPal remind](https://developer.paypal.com/api/invoicing/v2/invoices-remind/), [PayPal cancel](https://developer.paypal.com/api/invoicing/v2/invoices-cancel/).
